# P0 根因缩小：0x53D2EF 的 0x18 指针来源

2026-10-13 · `ScreenWings.exe` SHA-256 `481ecd41bef2a33076729680747eb92e4e2964bed89c58825d80f602de19f214`

## 本轮真正执行了什么

在当前 Linux 沙箱内，重新读取先前归档的原始样本与 **6,758,400 字节**第一层解包镜像（SHA-256：`2a1185bbcc93a049d413a71104ed41623bae61cf2412de5ea015564ea8b4d420`），再次运行前次离线归档中的有限 x86 模型 `trace_vm_handoff_p0.py`：

- 852 个模型指令/跳转步骤；
- 37 次写入，其中 32 次写虚拟机上下文、5 次写合成模拟栈；
- 仍在 **`0x53D2EF`** 尝试读取 `[0x18]` 时停止。

随后加入寄存器逐条跟踪和写入来源记录，独立复核原始恢复镜像里的 8 处关键 x86 指令编码，并由模型写入 CSV 确认字段写入。它不是 Windows 实机 CPU 执行或内存快照。

## 已闭合的条件性数据来源链

在本模型中 `EBP = CTX = 0x4C19BC`：

| 事件 | 指令 | 值 / 地址 |
|---|---|---|
| 先前处理器更新 `CTX+0x7E` | 写入结束 PC `0x5C2F1C` | `[0x4C1A3A] = 0xE8480977` |
| 先前处理器更新 `CTX+0x09` | 写入结束 PC `0x5C2F32` | `[0x4C19C5] = 0x92A45B90` |
| 第一轮减法 | `0x5C3000 SUB EAX,[EDX]` | `0x7AEC651F - 0xE8480977 = 0x92A45BA8` |
| 第二轮减法 | `0x5C3033 SUB EAX,[ESI]` | `0x92A45BA8 - 0x92A45B90 = 0x18` |
| 存入上下文 `+0x7A` | `0x5C30B8 ADD [ESI],EAX` | `[0x4C1A36] = 0x18` |
| 读取它 | `0x5C3118 MOV ESI,[ESI]` | `ESI = 0x18` |
| 写入 `+0x3B` | `0x5C3123 ADD [EDX],ESI` | `[0x4C19F7] = 0x18` |
| 第一次指针解引用 | `0x53D2ED MOV EDI,[EDI]` | `EDI = 0x18` |
| 第二次指针解引用 | `0x53D2EF MOV EDI,[EDI]` | 读取 `[0x18]`，模型中未映射 |

`CTX+0x3B` 起初在模型中被先前处理器清零（记录 PC `0x5933CB`），随后由 `0x5C3123` 重新写入 0x18，且整个已记录前缀中无更晚的重叠写入。因此，**此前将问题归咎于 `CTX+0x3B` 未初始化的猜测不成立**：它有明确的上游写入操作。

注意上述“记录 PC”来自前一模型：模型在执行每条指令前已将 `pc` 增加到下一条指令，因此记录器的 PC 不总是实际执行存储指令的地址。这一点在验证器中明确区分。

## 分支敏感性试验

在不修改源 EXE 的临时模型中，分别将 `0x5C2F65`、`0x53D0D9` 的 `JBE` 人为改为“不跳”，结果都仍到达同一个 `[0x18]` 读取。模型路径步数分别为 855、856，而原路径为 852。此试验只说明这两个假设分支对当前异常没有改变，**不是证实实际运行时这些分支可能走向哪一侧**。

`0x593114` 改为不跳导致模型内存写入越过规定的上下文/模拟栈区域，因此不能拿该分支的结果做 OEP 结论。

## 复现方式

已发布：`tools/diagnose_p0_edi_provenance.py`、`analysis/p0_model_memory_writes.csv`（37 条）、`analysis/p0_edi_provenance.json`。

```bash
python3 tools/diagnose_p0_edi_provenance.py \
    analysis/stage1/schiffer_stage1.bin \
    analysis/p0_model_memory_writes.csv \
    --out analysis/p0_edi_provenance_verified.json
```

该脚本校验全部恢复区哈希、关键原生指令、全部 37 条写入中的五条关键写入和最后写入者，重新计算 `0x18`。既不会执行目标 EXE，也不能将模型来源的数值升级成真实运行寄存器证据。

## 下一轮 P0 严格需要的真实证据

与其简单在 `0x53D2EF` 打断点，应先比较**四个先后地址**的真实寄存器/内存：

1. `0x5C3033`：第一次差值是否为 `0x18`？校验 `EAX`、`ESI`、`[ESI]`、`[EBP+0x09]`、`[EBP+0x7E]`。
2. `0x5C3123`：写前 `ESI`、`EDX`、`[EDX]` 是否符合模型？
3. `0x53D2ED`：`EDI` 是否真实指向 `EBP+0x3B`？`[EDI]` 是否为 0x18？
4. `0x53D2EF`：`EDI` 是否真为 0x18，还是模拟初始状态或解释器语义已经偏离？

可使用 WinDbg 的**硬件执行断点**（软件 `INT3` 可能影响受保护程序），并记录 ASLR 后模块基址。请见 `docs/p0-windbg-native-probe.md`。若以上地址从未命中，则也必须检查运行时实际解包/保护重定位是否改变了代码地址，不能据此断言路径不可达。

**当前证据界限：** 没有运行 Windows VM，没有跨过保护层，没有恢复原始业务 OEP，也没有 `SetWindowDisplayAffinity`、`WDA_MONITOR` 或截屏窗口调用的函数级证明。
